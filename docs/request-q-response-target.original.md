下面只定义 **TPF–Q Budget 响应曲线的目标、需要表达的性质，以及它在 Serving 调度中的用途**。不涉及曲线的采样、拟合、预测模型或具体求解算法。

# BDLM Serving：TPF–Q Budget 响应曲线的目标与要求

## 一、核心目标

我们希望为 BDLM 的每个 Request 建立一条**随请求实际执行状态变化的 TPF–Q Budget 响应曲线**。

这条曲线需要回答：

> 对于一个正在执行的 Request，如果当前分配不同的 Q 计算预算，其后续有效解码效率（TPF）分别会发生什么变化？增加或减少预算的边际收益与损失是多少？

它不是一个模型对应一条固定曲线，而是**同一个 Request 在不同执行状态下，可以呈现不同的预算收益曲线**。

最终目的，是将单请求的预算收益信息提供给 Serving Scheduler，使其能够根据当前 Batch 的负载和 GPU 执行成本，联合决定每个 Request 应分配的 Q 预算。

## 二、Q Budget 的定义

研究对象为支持动态滑动 Q 窗口的原生 BDLM。

| 模型             | 原生 Block Size | Rolling Q Budget          |
| -------------- | ------------- | ------------------------- |
| LLaDA 2.1      | 32            | 4 / 8 / 16 / 32 / 64      |
| DiffusionGemma | 256           | 32 / 64 / 128 / 256 / 512 |

需要明确区分：

**1. Rolling Q Budget**

正常滚动推理时，每轮允许使用的 Q 计算预算。

**2. Block Admission**

当当前 Block 接近完成、需要引入后续 Block 时，执行器需要为新 Block 的全部 MASK 位置进行初始化计算。

因此，Admission 可能要求高于当前 Rolling Q Budget 的一次性计算开销。

例如，LLaDA 使用 Rolling Q8，并不意味着整个请求的每一次 Forward 都严格不超过 Q8。

**TPF 响应曲线必须反映完整的实际执行过程，而不是只统计 Rolling 阶段。**

## 三、TPF 响应曲线需要满足的要求

### 1. 状态相关性

TPF–Q 关系必须能够反映当前 Request 的实际执行状态。

不能仅根据推理轮次判断当前处于 Early、Middle 或 Late 阶段，因为：

- 不同请求的生成长度未知。
- 不同请求的去噪轮次差异很大。
- 同一请求可能经历多个 Block 的初始化、去噪、退休和滚动。
- 相同推理轮次不意味着相同剩余工作量。

我们需要描述的是当前状态下的预算收益，而不是请求执行到第几轮。

### 2. 历史依赖性

相同的 Request，即使当前位于同一个 Block、具有相同的剩余 MASK 数量，也不一定具有相同的 TPF–Q 曲线。

例如，前几轮分别使用：

- 32 → 32 → 32
- 8 → 16 → 8

两种轨迹可能产生不同的 Token、KV、去噪进展和缓存状态，进而影响下一次 Q 预算的收益。

因此，曲线必须反映历史执行所形成的**当前真实状态**，不能假设预算收益与此前的运行轨迹无关。

### 3. 不依赖未来生成长度已知

对于一个在线 Request，我们无法提前知道：

- 最终会生成多少 Token。
- 还需要多少个 Block。
- 什么时候遇到 EOS。
- 还需要多少次去噪。

曲线不应依赖这些未知的未来信息才能使用。

它应当能够在请求持续生成、Block 按需加入、Q 窗口不断向前滚动的情况下，描述当前预算选择的预期收益。

### 4. 体现完整的 Block 生命周期

预算收益不仅来自当前 Block 内的 Token 解码，还包括：

- 当前活动窗口的持续去噪。
- 已解码位置的重新访问及 T2T 更新。
- KV 的缓存、刷新和复用。
- 新 Block 的 Admission 与初始化。
- Block 的退休和窗口推进。
- 已有计算状态的保留、恢复或失效。

不能只观察单次 Forward 的 Token 接受数量，而忽略该预算选择对后续执行的影响。

### 5. 反映非线性和边际收益变化

TPF 随 Q Budget 增大，通常存在提高的可能，但不应预设其严格单调、线性或凹性。

我们希望曲线能够表达：

- 增加少量 Q 时，TPF 是否明显提高。
- Q 继续增大后，收益是否开始饱和。
- 某些状态下，额外预算是否几乎没有收益。
- 某些预算是否因为额外工作或执行轨迹变化，反而降低 TPF。

核心是描述预算变化带来的**边际 TPF 收益**。

### 6. 能够反映预算收缩的损失

曲线不仅需要说明扩大预算有什么好处，还需要说明缩小预算会付出什么代价。

例如：

- 从 Q32 缩小到 Q16，TPF 损失多少？
- 从 Q16 缩小到 Q8，是否存在明显的效率下降？
- 是否存在一些请求状态，其 Q 减半但 TPF 几乎不变？
- 是否存在一些状态，其预算稍微降低就会导致 TPF 显著恶化？

这是高负载 Serving 中决定哪些请求应该优先收缩预算的关键。

### 7. 以质量约束为前提

TPF 提升不能建立在不可接受的质量损失之上。

因此，不同预算的收益必须具有质量可比性。

质量评测沿用此前协议，包括 GSM8K、MATH500、HumanEval，以及原有的正确率、EOS、截断等口径。

TPF 继续采用此前定义：

[\
TPF_i=\frac{\text{最终有效输出 Token 数}}{\text{该请求的全部生成 Forward 数}}\
]

所有 Admission、KV Refresh、晋升校验、重编码等生成阶段 Forward 都必须计入分母。

完整请求的主指标仍是逐请求 TPF 的算术平均；局部响应曲线是用于决策的预测量，不应与完整请求 TPF 混为一谈。

## 四、曲线最终需要表达什么？

对于 Request (i)，在当前执行状态 (S_i) 下，定义：

[\
\boxed{P_i(q\mid S_i)}\
]

其中：

- (S_i)：当前 Request 的真实执行状态。
- (q)：候选 Rolling Q Budget。
- (P_i)：在该状态下采用预算 (q) 所对应的预期 TPF 响应。

我们需要关注的不只是 (P_i(q))，还有：

P_i(q_2\mid S_i)-P_i(q_1\mid S_i)\
]

它表示在相同当前状态下，改变预算能够带来多少 TPF 收益或损失。

最终，曲线应当帮助我们识别三种情况：

| 响应特征   | 含义              | 调度价值        |
| ------ | --------------- | ----------- |
| 高边际收益  | 增大 Q 可以明显提高 TPF | 值得优先获得额外预算  |
| 低边际收益  | 增大 Q 的 TPF 收益很小 | 可以保持较小预算    |
| 高收缩敏感性 | 减小 Q 会显著损害 TPF  | 高负载下应尽量保留预算 |

这些特征是动态变化的，同一个 Request 随着窗口推进，可能在不同类别之间切换。

## 五、这条曲线在 Serving 中的用途

Serving Scheduler 面临的问题是：

> 当前 Batch 有多个处于不同执行状态的 Request，GPU 的计算资源有限，应该给每个 Request 分配多少 Q Budget？

TPF 响应曲线提供每个请求的**预算收益侧信息**。

GPU 性能曲线提供整个 Batch 在不同 Q 组合下的**执行成本侧信息**。

调度器的任务是在两者之间寻找最优权衡。

### 场景 A：低负载

GPU 具有额外计算容量。

希望识别哪些 Request 扩大 Q 可以获得较大的 TPF 收益。

目标是：

**将额外预算优先分配给边际收益高的请求，提升整体执行效率，而不是让所有请求统一使用最大 Q。**

### 场景 B：高负载

Batch 较大，额外 Q 的 GPU 运行时间成本可能增加。

希望识别哪些 Request 对预算收缩不敏感。

目标是：

**优先收缩边际 TPF 损失较小的请求，保留高敏感请求的预算，以较小的整体 TPF 损失减少 GPU 计算负担。**

### 场景 C：突发负载

大量新请求突然到达，当前 Batch 和 GPU 资源压力迅速变化。

希望能够根据请求当前的 TPF 响应曲线重新分配预算。

目标是：

**不采用统一降档，而是有选择地收缩低收益预算，在有限 GPU 资源下尽量保持整个 Batch 的有效解码效率。**

负载恢复后，则重新扩大高边际收益请求的预算。

### 场景 D：同一请求的状态变化

即使 Batch Size 不变，请求也会因为 Token 解码、Block Admission、KV 更新和窗口推进而改变预算响应曲线。

目标是：

**使 Q 分配能够随请求的实际执行状态持续调整，而不是在请求进入 Batch 时固定一次预算。**

## 六、最终服务于一个联合优化目标

对于一个包含 (N) 个请求的 Batch：

[\
\mathbf q=(q_1,q_2,\ldots,q_N)\
]

各请求的 TPF 响应为：

[\
P_i(q_i\mid S_i)\
]

整个 Batch 的物理 GPU 运行时间为：

[\
T\_{\mathrm{GPU}}(\mathbf q)\
]

我们的目标是：

[\
\boxed{\
\max\_{\mathbf q}\
\frac{\
\frac{1}{N}\sum\_{i=1}^{N}P_i(q_i\mid S_i)\
}{\
T\_{\mathrm{GPU}}(\mathbf q)\
}\
}\
]

这是当前希望研究的 TPF—时间权衡目标；它与完整请求的最终 Goodput 不完全等价，后续需要通过端到端评测确认。

约束包括：

- 每个请求只能选择对应模型支持的 Q 档位。
- 不允许使用质量不可接受的预算配置。
- Block Admission 必须遵守对应模型的执行语义。
- GPU 物理执行成本和实际计算容量需要得到满足。

这里的核心是**联合决定整个 Batch 中所有请求的预算**，而不是每个请求独立选择最大 TPF 的 Q。

## 七、最终研究目标

我们希望得到一种能够反映真实请求执行状态的预算响应曲线，使系统知道：

1. **什么时候增加 Q 值得。**
2. **增加多少 Q 才值得。**
3. **什么时候减少 Q 损失较小。**
4. **哪些请求应该优先获得更多 Q。**
5. **哪些请求应该在高负载下优先收缩 Q。**

从而实现统一的资源分配逻辑：

**低负载时，利用空闲计算资源提高高收益请求的 TPF；高负载时，优先减少低收益预算；突发负载时，根据整体 GPU 时间成本重新分配各请求预算。**

最终追求的不是单个请求的最大 TPF，也不是让 GPU 强制运行在某个 Roofline 位置，而是：

> **在不同 Serving 负载下，根据每个 Request 当前的预算—TPF 收益关系，联合分配 Q 预算，使整个 Batch 的有效解码效率与 GPU 运行时间达到尽可能好的权衡，同时保持可接受的生成质量。**

---

**文档边界：** 本文仅规定 TPF 响应曲线需要表达什么、满足什么性质、解决什么调度问题；不规定如何划分状态、如何采样、如何拟合、使用什么预测器或采用什么优化算法。

最核心的要求可以压缩成一句话：

**我们需要的不是一条静态 Q–TPF 曲线，而是一个能够回答“当前请求再增加或减少一档 Q，会获得多少收益或损失”的状态相关响应关系，最终用于整个 Batch 的联合预算权衡。**
