# Gemma FIFO 切档：独立汇总与默认判断

由 `python -m experiments.t2t.serving_slots.fifo_summary` 生成。输入是已完成的 Gemma FIFO 90 题轨迹（4 种策略）和六份配对评分；脚本不重跑 GPU、不重新评分，只从原始请求记录、clock 和配对 CSV 重算并交叉核对。只接受 Gemma frozen90 运行，元数据不符直接报错，不套用其它模型或数据。

## 结论

**不建议把 FIFO 切档设为默认。** 在本次单卡、单次、合成到达计划的 90 题实验中：

- 四种策略全 90 都答对 **83/90**（正确总数相同，不证明等价）；六个配对的质量差 95% 区间全部跨 0（半宽约 ±6.9 到 ±9.9 个百分点），没有质量证据支持切档。
- `fixed_high`（恒 64 槽）TPF 最高（**12.897**）、响应均值最低（**5.837 s**），物理 Q 250,795。
- `busy_high`（忙时 64、闲时 32）与 `fixed_high` 的正确总数、Q、响应接近，但 TPF 低 **1.085**（95% CI [-1.480, -0.690]），forward 多 **10.3%**；Q 只少 **0.55%**，没有明显优势。
- `busy_low`（忙时 32、闲时 64）物理 Q 少 **4.09%**，但 TPF 低 **3.822**、响应均值慢 **72.7%**（+4.241 s）；`fixed_low` 的 Q 少 **4.23%**、响应慢 **85.1%**、TPF 低 **4.434**。低档省 Q 的代价是更多 forward 和更长时延。
- 在本数据上默认仍应是 `fixed_high`。只有在名义 Q 预算受限（名义 Q 可能溢出，物理 Q 以实测为准）、且能接受约 +73% 响应时间时，才考虑 `busy_low`；`busy_high` 在本数据上的 Q 节省很小，平均响应未改善，不建议作为默认或省 Q 方案。

四个策略在 (正确总数, TPF, 物理 Q, 响应) 上都处于 Pareto 前沿（fixed_high、busy_low、busy_high、fixed_low）：正确总数相同（不证明等价），Q 与时延/推进速度互相牺牲。默认应按目标选；按通用目标（TPF 与时延优先、Q 作次要约束）选 `fixed_high`。

## 全 90 数值

| 策略 | 忙时槽 | 闲时槽 | 正确 | TPF | 效率 | N | F | 物理 Q | Q/F | 响应均值 | 响应 p95 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| fixed_high | 64 | 64 | 83 | 12.897 | 12.71% | 31879 | 2562 | 250,795 | 97.89 | 5.837 s | 11.044 s |
| busy_low | 32 | 64 | 83 | 9.075 | 13.57% | 32630 | 3819 | 240,535 | 62.98 | 10.078 s | 18.398 s |
| busy_high | 64 | 32 | 83 | 11.812 | 12.82% | 31967 | 2826 | 249,406 | 88.25 | 5.867 s | 11.348 s |
| fixed_low | 32 | 32 | 83 | 8.463 | 13.73% | 32982 | 4023 | 240,190 | 59.70 | 10.802 s | 19.593 s |

- 正确 = 90 题答对数；TPF = 逐题 `N/F` 的均值；效率 = `ΣN/Σ物理 Q`；Q 为物理 padded rows（含批内 padding，纯 prompt prefill 除外）。
- `fixed_high`/`fixed_low` 恒定 64/32；`busy_high` 忙时 64、闲时 32；`busy_low` 忙时 32、闲时 64。忙 = 等待队列深度 ≥ 2，闲 = 0，等于 1 继承前态。
- 到达计划使队列在 60%–80% 的选位轮处于忙态；`busy_low` 与 `busy_high` 分别只有 9/90、15/90 个请求同时看到两种档位。两种切档策略大部分时间表现接近其主导档位，本实验不能单独识别“切换”本身的价值。

- 六个 TPF 区间都排除 0；六个质量区间都跨 0。方向：TPF `fixed_high` > `busy_high` > `busy_low` > `fixed_low`；物理 Q 相反（越小越省）；响应 `fixed_high` ≈ `busy_high` < `busy_low` < `fixed_low`。

## 检查

- **计时有效**：单位 2062.080 ms；p95 入队延迟 0.175–0.232 ms、组内间距误差 p95 0.066–0.132 ms（判据均为 25.776 ms）、到达跨度相对误差 ≤ 1.31e-06（判据 1%）。四臂全部通过；逐请求核对 `planned ≤ enqueued ≤ start < finish`、单服务台不重叠、offer tick/深度/预算映射；clock 为 `monotonic_ns`，计时排除写盘与评分。
- **请求不重复**：四臂各恰好 90 份请求文件，index 0–89 无重复；clock 顺序等于登记 trace；六个配对各有 90 个唯一配对 index；每个策略在六份配对文件中重复出现时逐窗口指标一致。无失败、无截断。
- **方向**：`busy_low` 忙→32/闲→64、`busy_high` 忙→64/闲→32、两个 fixed 恒定；实测 offer（低/高）0/2098、3078/264、597/1763、3539/0。配对方向见上表：正确总数都相同（不证明等价），TPF 的 6/6 个区间排除 0。
- **work**：360 份请求全部通过 `verify_work`（`F>0`、`Q≥F`、`Q==物理 Q`、`N≥0`、`tpf==N/F`、`token_efficiency==N/Q`）；逐窗口 N/F/物理 Q 与六份配对 CSV 及 `fifo-clock.csv` 逐项相等。Q 是行数，不是 GPU 时间；TPF 是每 forward 的 token 数，不是墙钟速度。

## 复现

汇总（CPU，无需 GPU；路径按本机替换）：

```bash
cd <repo>
PYTHONPATH=. <python> -m experiments.t2t.serving_slots.fifo_summary \
  --run <fifo-run> --scores <fifo-scores> --cases <samples.json> \
  --out experiments/t2t/serving_slots/fifo
```

上游评分（CPU）：`PYTHONPATH=. <python> -m experiments.t2t.serving_slots.fifo_report --run <fifo-run> --cases <samples.json> --out <fifo-scores>`。

FIFO 轨迹由 `launch_prefix90.py` 在 GPU0 的 holder 协议下生成；重跑需要 holder 与权重，不属于本汇总。`samples.json` SHA-256 `bc9e457ddebd1eb0062c495f13f31cfc86b18e3cebbd90c3da08674f7ab65aed`。

## 限制

1. 单次运行、单卡（H800 PCIe，GPU0）、单一合成到达计划；没有生产流量、重复实验或稳定 p95。
2. 质量检验功效不足：90 题、六个质量区间都跨 0，不能排除若干个百分点的真实差异；正确总数相同不证明等价。
3. 队列在 60%–80% 的轮次忙，`busy_low`/`busy_high` 大部分时间接近主导档位，只有 9/15 个请求看到两种档位；本实验不能单独识别“切换”本身的价值。
4. 队列深度内生，各策略不强行等深；TPF 不是墙钟速度，Q 不是 GPU 时间；名义 Q 可能溢出，物理 Q 以实测为准。
5. 六个配对 × 三个窗口未做多重比较校正；只分析已完成的 `gemma-fifo90`（早先的 in-memory 尝试因 prefill 审计失败被排除）。
6. 结论只适用于 DiffusionGemma 26B-A4B（B=256）与本工作负载；单请求执行器不是多请求调度器。
